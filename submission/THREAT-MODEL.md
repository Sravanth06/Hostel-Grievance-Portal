# Threat Model — HostelGrievance

## 1. Scope

This threat model covers the HostelGrievance web application and its
supporting server-side resources.

The main components are:

- Student browser
- Warden browser
- Svelte frontend
- Hono HTTP API
- Authentication and session handling
- SQLite database
- Attachment filesystem storage
- Application runtime
- Network/reverse-proxy boundary
- Security audit logging

The objective is to identify realistic attack paths and reduce the impact
of a successful compromise while preserving normal application workflows.

## 3. Actors

### Student

A legitimate student can:

- Authenticate.
- Create grievances.
- View their own grievances.
- Edit their own editable grievances.
- Add comments.
- Add attachments.
- Retrieve their own attachments.

A student must not be able to perform Warden-only actions or access
another student's resources.

### Warden

A legitimate warden can:

- Authenticate.
- Review grievances.
- View grievance comments.
- Comment on grievances.
- Update grievance status.
- Access grievance attachments as part of management workflows.

A warden must not modify student-authored grievance content through
Warden-only workflow operations.

### Unauthenticated attacker

An internet user without a valid session may attempt to:

- Access protected API endpoints.
- Guess grievance identifiers.
- Guess attachment identifiers.
- Submit malicious input.
- Upload malicious files.
- Abuse authentication endpoints.
- Trigger application errors.
- Exploit CORS or browser security weaknesses.

### Authenticated malicious user

A compromised or malicious student account is especially important because
the attacker already has a valid session.

Possible goals include:

- Accessing another student's grievance.
- Accessing another student's attachment.
- Modifying another student's grievance.
- Escalating from Student privileges to Warden privileges.
- Manipulating uploaded files.
- Abusing application input.

The security model therefore does not assume that authentication alone
makes a user trustworthy.

---

## 4. Trust Boundaries

### Boundary 1 — Browser to frontend

The browser is untrusted.

Everything controlled by the browser must be treated as attacker-controlled,
including:

- Request parameters
- JSON bodies
- Form fields
- Filenames
- MIME types
- Cookies
- Resource identifiers

Frontend controls are treated as usability features rather than security
boundaries.

---

### Boundary 2 — Frontend to API

The API is the authoritative security boundary.

The server independently determines:

- Whether the user is authenticated.
- Which user is making the request.
- Which role the user has.
- Whether the user owns a resource.
- Whether the requested operation is allowed.

Changing frontend JavaScript or manually constructing HTTP requests must not
bypass these controls.

---

### Boundary 3 — Authentication/session to application

The session cookie contains an opaque session identifier.

The server resolves the identifier against the sessions table and obtains
the authenticated user's identity.

Authorization decisions are therefore based on server-side session state.

Expired sessions are rejected and removed.

---

### Boundary 4 — API to database

The database is a server-side trusted resource.

The browser does not directly access SQLite.

SQL operations use parameterized statements.

Foreign-key constraints are enabled.

The database contains security-sensitive information and must remain
outside public network access.

---

### Boundary 5 — API to filesystem

Uploaded attachments cross from an untrusted browser into the server
filesystem.

The application therefore validates:

- Declared MIME type
- File size
- Actual file signature

The physical filename is generated by the server.

User-controlled filenames are stored only as metadata.

Path traversal protections are applied when accessing stored files.

---

### Boundary 6 — Application to runtime/host

The application process is assumed to be less privileged than the host.

Production deployment should run the application with only the filesystem
and operating-system permissions required for normal operation.

Compromise of the application should not automatically provide unrestricted
access to unrelated host resources.

## 6. Threat Analysis

| Threat | Attacker | Impact | Existing Mitigation | Residual Risk |
|--------|----------|--------|---------------------|---------------|
| Credential attack | Unauthenticated attacker | Account takeover | Argon2id password hashing and generic authentication errors | Weak or reused passwords remain possible |
| Session theft | Attacker with stolen cookie | Account impersonation | HttpOnly, SameSite, Secure in production, expiry, server-side sessions | A stolen valid session remains usable until expiry or invalidation |
| Grievance IDOR | Malicious student | Unauthorized grievance disclosure or modification | Server-side ownership checks | Future endpoints must preserve authorization checks |
| Attachment IDOR | Malicious student | Unauthorized file disclosure | Attachment-to-grievance ownership checks | Future attachment endpoints require the same checks |
| Privilege escalation | Malicious student | Unauthorized Warden actions | Server-side role enforcement | Warden accounts have higher impact |
| Malicious upload | Authenticated attacker | Storage or file-handling abuse | Size, MIME, signature validation and random filenames | Magic-byte validation is not malware scanning |
| Path traversal | Attacker | Unauthorized filesystem access | Filename restrictions and resolved-path boundary checks | Host filesystem permissions remain important |
| CORS abuse | Malicious website | Credentialed cross-origin requests | Explicit trusted-origin allowlist | Misconfigured production origins remain a risk |
| Information disclosure | Unauthenticated attacker | Exposure of internal details | Centralized controlled error handling | Protected server logs remain sensitive |
| Security-event evasion | Attacker | Reduced investigation capability | Authentication audit logging | Logs require monitoring and retention |
| Database integrity abuse | Application attacker | Inconsistent security relationships | Parameterized SQL and foreign-key constraints | Database still requires filesystem protection |
| Frontend bypass | Authenticated attacker | Unauthorized API actions | Server-side authentication, authorization and validation | Every future endpoint must enforce server-side controls |

---

## 7. Security Assumptions

The threat model assumes:

- Production uses HTTPS.
- The database is not directly exposed to the network.
- The upload directory is not directly exposed as an unrestricted public filesystem.
- Production `HOSTEL_ALLOWED_ORIGINS` contains only trusted origins.
- Application and database filesystem permissions are appropriately restricted.
- Server logs are protected from unauthorized access.
- Warden credentials are protected operationally.

These assumptions are deployment responsibilities rather than guarantees
provided solely by application code.

---

## 8. Highest-Priority Threats

The highest-impact threats for this application are:

1. **Student-to-student data access** through IDOR.
2. **Attachment disclosure** through guessed or manipulated identifiers.
3. **Student-to-Warden privilege escalation.**
4. **Account or session compromise.**
5. **Malicious file upload and filesystem abuse.**

The implemented security controls prioritize these threats while preserving
the required grievance-management workflows.

## 10. Residual Risk

The application-level controls reduce the identified attack surface but do
not eliminate all deployment risk.

Remaining areas include:

- Password reuse or weak user-selected credentials.
- Stolen sessions before expiry.
- Missing production rate limiting.
- Incorrect CORS deployment configuration.
- Malware or vulnerabilities hidden inside otherwise valid image formats.
- Insecure host or filesystem permissions.
- Insufficient production log monitoring or retention.

These risks require appropriate operational and deployment controls.
