# Hardening Register — HostelGrievance

This document records the security findings identified during the
pre-launch hardening exercise, the security consequence of each finding,
the remediation performed, verification evidence, and remaining risk.

The finding IDs below are project-specific and are not challenge-provided
identifiers.

---

## Hardening Register

| ID | Finding | Risk | Change | Verification | Residual Risk |
|----|---------|------|--------|--------------|---------------|
| HG-SEC-001 | Weak/legacy password protection | Credential compromise if password hashes are exposed or attacked offline | Added Argon2id password hashing and automatic upgrade of legacy hashes after successful authentication | Successful student and Warden login; TypeScript and test suite pass | Compromised passwords remain a user risk; password rotation and rate limiting should be added operationally |
| HG-SEC-002 | Authentication depended on client-visible application state | An attacker could attempt to manipulate frontend state and bypass intended access restrictions | Authentication is determined from an opaque server-side session stored in SQLite | `/api/me` succeeds only with a valid session; logout invalidates the session | Host/application compromise could still expose session infrastructure |
| HG-SEC-003 | Session lifetime and cookie protections required hardening | Stolen session credentials could have excessive lifetime or be exposed to frontend JavaScript | Added session expiry enforcement, `HttpOnly`, `SameSite=Lax`, and production `Secure` cookie handling | Login/logout/current-user tests pass; cookie attributes inspected during verification | Session theft before expiry remains possible |
| HG-SEC-004 | Student object-level authorization | A student could potentially access another student's grievance by changing a grievance ID | Server checks the authenticated user's ID against the grievance owner before returning or modifying student resources | Existing test confirms another student's grievance returns `403` | A future endpoint could reintroduce IDOR if authorization checks are omitted |
| HG-SEC-005 | Attachment object-level authorization | Guessing an attachment ID could expose another student's uploaded file | Attachment retrieval resolves the owning grievance and verifies the authenticated user's authorization before reading the file | Existing attachment test confirms another student's attachment returns `403` | Correct authorization must continue to be applied to future attachment endpoints |
| HG-SEC-006 | Student/Warden privilege separation | A malicious student could attempt to perform Warden-only workflow operations | Role checks are enforced server-side; students cannot change grievance status and Wardens cannot modify student-authored content through the Warden workflow | Existing status-management test confirms student status change is forbidden and Warden management works | Privileged Warden accounts remain higher-impact accounts and require operational protection |
| HG-SEC-007 | Browser-controlled input | Malformed or unexpected user input could cause invalid application state or unexpected behaviour | Added server-side validation for grievance fields, categories, statuses, comments, and uploaded files | Existing API tests cover valid operations and invalid attachment requests; TypeScript passes | Application logic must continue validating every newly introduced input |
| HG-SEC-008 | User-controlled attachment filenames | A malicious filename could cause path traversal or filesystem manipulation if used directly | Original filenames are treated as metadata; physical storage filenames are randomly generated by the server | Attachment upload/retrieval tests pass | Filesystem permissions and deployment configuration remain important |
| HG-SEC-009 | Upload MIME type could be spoofed | An attacker could claim arbitrary content was an allowed image type | Attachment validation now checks actual file signatures/magic bytes in addition to declared MIME type | Valid PNG attachment continues to work; invalid/disallowed attachments are rejected; TypeScript and 14/14 tests pass | Magic-byte checks are not a complete malware-analysis solution |
| HG-SEC-010 | Oversized attachment uploads | Large uploads could consume excessive memory or storage | Enforced a 2 MB maximum attachment size and rejected empty files | Existing oversized attachment test passes with `400` | Network-level request limits and rate limiting should also be used in production |
| HG-SEC-011 | Filesystem path traversal | A crafted path could attempt to read files outside the upload directory | Stored filenames reject path separators/traversal sequences and resolved paths are checked against the upload-directory boundary | Attachment storage/retrieval tests pass | Host-level filesystem compromise remains outside application-level controls |
| HG-SEC-012 | Credentialed CORS reflected arbitrary origins | A malicious website could potentially abuse browser credentials against the API | Credentialed CORS is restricted to explicitly configured trusted origins through `HOSTEL_ALLOWED_ORIGINS` | Trusted local origins remain supported; arbitrary origins are not reflected | Production must configure only trusted university origins |
| HG-SEC-013 | Internal application errors could expose implementation details | SQL, filesystem, runtime, or stack information could help an attacker | Added centralized error handling that logs unexpected errors server-side while returning a generic client response | Unknown-resource/error tests pass; internal implementation details are not returned | Server logs must themselves be protected and monitored |
| HG-SEC-014 | Limited security visibility | Suspicious authentication activity could be difficult to investigate | Added an audit log containing security-relevant events, request metadata, timestamps, and user IDs where available | Audit records are generated for authentication events; sensitive secrets are deliberately excluded | Audit logs require operational monitoring, retention, and access controls |
| HG-SEC-015 | Audit records could become a source of secret leakage | Logging passwords, session tokens, or file contents could create a second sensitive-data store | Audit logging explicitly excludes passwords, session tokens, and uploaded file contents | Audit-log verification confirms login credentials and session cookie values are not stored in audit data | Other future logging code must follow the same rule |
| HG-SEC-016 | Database relationship enforcement | Invalid references between security-sensitive records could create inconsistent authorization state | Enabled SQLite foreign keys and retained relational constraints between users, sessions, grievances, comments, attachments, and audit records | Database initialization/reset and application tests pass | SQLite remains a local application database and requires filesystem protection |
| HG-SEC-017 | Unknown resources and unauthorized access could expose implementation details | Resource enumeration and error handling could reveal unnecessary information | Protected resource lookups return controlled application errors and authorization is performed before sensitive data is returned | Existing tests confirm unauthorized grievance access and unknown grievance handling | Response differences such as timing may still provide limited enumeration signals |
| HG-SEC-018 | Security boundary depended too heavily on the frontend | UI restrictions can be bypassed by directly calling APIs | Moved security decisions to server-side authentication, role checks, ownership checks, validation, and resource access controls | API tests exercise protected endpoints directly without relying on the UI | Every future API endpoint must follow the same server-side enforcement model |

# Detailed Findings

## HG-SEC-001 — Password Protection

### Finding

Authentication credentials require strong password protection because a
database compromise can expose password hashes for offline cracking.

### Risk

Weak or legacy password hashing increases the chance that an attacker who
obtains the database can recover user passwords.

### Change

The authentication implementation uses Argon2id for password hashing.

Legacy hashes are upgraded after successful authentication so existing
seeded users remain functional without requiring an immediate password
reset.

### Verification

Successful authentication for the seeded Student and Warden accounts was
verified.

The server TypeScript compilation and complete API test suite also pass.

### Residual Risk

Password compromise remains possible if users choose weak passwords.
Production deployments should additionally consider rate limiting,
credential monitoring, and password-reset controls.

---

## HG-SEC-002 — Server-Side Sessions

### Finding

Authentication must not depend on frontend state.

### Risk

A malicious user can modify browser state, JavaScript variables, or direct
HTTP requests.

### Change

Authentication uses an opaque server-generated session token stored in the
server-side sessions table.

The authenticated identity is reconstructed by the server from the
session.

### Verification

The existing tests verify that:

- Login creates a usable authenticated session.
- `/api/me` works with the session.
- `/api/me` fails without authentication.
- Logout invalidates the session.

### Residual Risk

A valid stolen session remains usable until it expires or is destroyed.

---

## HG-SEC-003 — Session Cookie Hardening

### Finding

Authentication cookies require browser-level protections.

### Risk

A session token exposed to frontend JavaScript or sent in unsafe
cross-site contexts can increase session compromise risk.

### Change

The session cookie uses:

- `HttpOnly`
- `SameSite=Lax`
- `Secure` in production
- Finite expiration

Expired sessions are deleted server-side.

### Verification

Login and logout tests pass and the authentication cookie is inspected for
the expected security attributes.

### Residual Risk

HTTPS must be correctly configured in production.

---

## HG-SEC-004 — Grievance Authorization

### Finding

Resource IDs supplied by clients cannot be treated as proof of ownership.

### Risk

An attacker could change a grievance ID in a request and attempt to read
another student's grievance.

### Change

The API compares the authenticated student's ID with the grievance's
`student_id`.

### Verification

The test suite explicitly verifies that a student cannot retrieve another
student's grievance.

### Residual Risk

Future endpoints must implement the same object-level authorization model.

---

## HG-SEC-005 — Attachment Authorization

### Finding

Attachment identifiers are also attacker-controlled object references.

### Risk

Guessing an attachment ID could expose another user's sensitive uploaded
file.

### Change

The server first determines which grievance owns the attachment and then
checks authorization before reading the physical file.

### Verification

The attachment test confirms that another student receives `403`.

### Residual Risk

Future attachment operations must preserve ownership checks.

---

## HG-SEC-006 — Student/Warden Separation

### Finding

Students and Wardens have different responsibilities.

### Risk

A compromised student account could become significantly more damaging if
role checks existed only in the frontend.

### Change

Role and ownership checks are performed by the API.

Students cannot change grievance status.

Wardens can manage status but cannot modify student-authored grievance
content through the Warden workflow.

### Verification

Existing status-management tests confirm the intended Student and Warden
behaviour.

### Residual Risk

Warden accounts have greater privileges and therefore require stronger
operational protection.

---

## HG-SEC-007 — Untrusted Input

### Finding

All client-supplied input is potentially malicious.

### Risk

Unexpected input could result in invalid application state or unexpected
application behaviour.

### Change

The API validates:

- Titles.
- Descriptions.
- Categories.
- Status values.
- Comment content.
- Attachment metadata.
- Attachment size.
- Attachment content signatures.

Parameterized SQL statements are used for database operations.

### Verification

The API test suite passes including invalid-input and attachment tests.

### Residual Risk

New endpoints must continue using the same validation model.

---

## HG-SEC-009 — File Signature Validation

### Finding

A browser-provided MIME type is not trustworthy.

### Risk

An attacker could submit arbitrary bytes while declaring a permitted
image MIME type.

### Change

Uploaded bytes are inspected for expected magic-byte signatures for:

- JPEG
- PNG
- GIF
- WebP

The declared MIME type must also be one of the configured permitted types.

### Verification

Valid PNG uploads continue to work.

The complete existing test suite passes after the change.

### Residual Risk

Signature validation establishes file-format consistency but does not
perform full malware analysis or guarantee that every image-processing
implementation is safe.

---

## HG-SEC-011 — Filesystem Boundary

### Finding

Filesystem paths are a security boundary.

### Risk

Path traversal could allow an attacker to request files outside the
attachment storage directory.

### Change

The application:

1. Rejects path separators.
2. Rejects traversal sequences.
3. Generates physical filenames server-side.
4. Resolves the final path.
5. Verifies that the final path remains inside the configured upload
   directory.

### Verification

Attachment retrieval continues to work with valid stored files and the
existing test suite passes.

### Residual Risk

The upload directory must not be directly exposed by the production web
server.

---

## HG-SEC-012 — CORS

### Finding

Credentialed CORS must not reflect arbitrary origins.

### Risk

If arbitrary origins were reflected while credentials were enabled,
cross-origin browser requests could become a security concern.

### Change

The API allows only explicitly configured origins.

The configuration is controlled using:

`HOSTEL_ALLOWED_ORIGINS`

Development defaults support the local frontend.

### Verification

The application CORS configuration was changed from arbitrary origin
reflection to explicit trusted-origin validation.

### Residual Risk

An incorrectly configured production allowlist could still introduce
cross-origin risk.

---

## HG-SEC-013 — Error Handling

### Finding

Internal errors can contain sensitive implementation information.

### Risk

Database paths, filesystem locations, SQL errors, stack traces, and
runtime details can assist attackers.

### Change

Unexpected errors are handled centrally.

Detailed information is logged server-side while the client receives a
generic error.

### Verification

The application test suite continues to pass and unknown-resource
handling does not expose internal implementation information.

### Residual Risk

Server logs must be protected from unauthorized access.

---

## HG-SEC-014 — Security Visibility

### Finding

Security-relevant events require investigation capability.

### Risk

Without security logging, suspicious authentication behaviour may be
difficult to reconstruct.

### Change

An audit log records security-relevant authentication activity with
investigation-oriented metadata.

### Verification

Audit events are generated during authentication operations.

### Residual Risk

Logging alone does not provide active detection. Production monitoring and
alerting should be added where available.

---

# Functional Preservation

The hardening changes were designed not to remove required business
functionality.

The following workflows remain available:

### Student workflow

- Login
- View grievances
- Create grievances
- Edit permitted grievances
- Add comments
- Upload attachments
- Retrieve authorized attachments

### Warden workflow

- Login
- View grievances
- View comments
- Add comments
- Update grievance status
- Access authorized attachments

The automated API test suite confirms the existing workflows remain
functional.
