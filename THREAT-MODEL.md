# Threat Model — HostelGrievance

## 1. Scope

This threat model covers the HostelGrievance web application and its
supporting server-side resources.

The main components are:

- Student browser
- Warden browser
- Svelte frontend
- Hono HTTP API
- Authentication and session handling
- SQLite database
- Attachment filesystem storage
- Application runtime
- Network/reverse-proxy boundary
- Security audit logging

The objective is to identify realistic attack paths and reduce the impact
of a successful compromise while preserving normal application workflows.

---

## 2. Assets

The primary assets requiring protection are:

### User information

- Student names
- Email addresses
- Room information
- User roles
- Authentication credentials

### Authentication state

- Server-side sessions
- Session identifiers
- Authentication cookies

### Grievance information

- Grievance titles
- Descriptions
- Categories
- Status
- Student ownership
- Timestamps

### Communication

- Student comments
- Warden comments

### Attachments

- Uploaded image files
- Original filenames
- Attachment metadata
- Physical stored files

### Security information

- Audit events
- Request metadata
- Authentication activity

### Application resources

- SQLite database
- Upload directory
- Application process
- Runtime environment

---

## 3. Actors

### Student

A legitimate student can:

- Authenticate.
- Create grievances.
- View their own grievances.
- Edit their own editable grievances.
- Add comments.
- Add attachments.
- Retrieve their own attachments.

A student must not be able to perform Warden-only actions or access
another student's resources.

### Warden

A legitimate warden can:

- Authenticate.
- Review grievances.
- View grievance comments.
- Comment on grievances.
- Update grievance status.
- Access grievance attachments as part of management workflows.

A warden must not modify student-authored grievance content through
Warden-only workflow operations.

### Unauthenticated attacker

An internet user without a valid session may attempt to:

- Access protected API endpoints.
- Guess grievance identifiers.
- Guess attachment identifiers.
- Submit malicious input.
- Upload malicious files.
- Abuse authentication endpoints.
- Trigger application errors.
- Exploit CORS or browser security weaknesses.

### Authenticated malicious user

A compromised or malicious student account is especially important because
the attacker already has a valid session.

Possible goals include:

- Accessing another student's grievance.
- Accessing another student's attachment.
- Modifying another student's grievance.
- Escalating from Student privileges to Warden privileges.
- Manipulating uploaded files.
- Abusing application input.

The security model therefore does not assume that authentication alone
makes a user trustworthy.

---

## 4. Trust Boundaries

### Boundary 1 — Browser to frontend

The browser is untrusted.

Everything controlled by the browser must be treated as attacker-controlled,
including:

- Request parameters
- JSON bodies
- Form fields
- Filenames
- MIME types
- Cookies
- Resource identifiers

Frontend controls are treated as usability features rather than security
boundaries.

---

### Boundary 2 — Frontend to API

The API is the authoritative security boundary.

The server independently determines:

- Whether the user is authenticated.
- Which user is making the request.
- Which role the user has.
- Whether the user owns a resource.
- Whether the requested operation is allowed.

Changing frontend JavaScript or manually constructing HTTP requests must not
bypass these controls.

---

### Boundary 3 — Authentication/session to application

The session cookie contains an opaque session identifier.

The server resolves the identifier against the sessions table and obtains
the authenticated user's identity.

Authorization decisions are therefore based on server-side session state.

Expired sessions are rejected and removed.

---

### Boundary 4 — API to database

The database is a server-side trusted resource.

The browser does not directly access SQLite.

SQL operations use parameterized statements.

Foreign-key constraints are enabled.

The database contains security-sensitive information and must remain
outside public network access.

---

### Boundary 5 — API to filesystem

Uploaded attachments cross from an untrusted browser into the server
filesystem.

The application therefore validates:

- Declared MIME type
- File size
- Actual file signature

The physical filename is generated by the server.

User-controlled filenames are stored only as metadata.

Path traversal protections are applied when accessing stored files.

---

### Boundary 6 — Application to runtime/host

The application process is assumed to be less privileged than the host.

Production deployment should run the application with only the filesystem
and operating-system permissions required for normal operation.

Compromise of the application should not automatically provide unrestricted
access to unrelated host resources.
